# Assignment 3 — Load balancing with Envoy (additions to the A1/A2 READMEs)

## What changed
| Area | Change |
|---|---|
| Replicas | `veritas-a/b/c` (REPLICA_ID A/B/C). Each replica = **one process serving HTTP :8000 and gRPC :50051** (gRPC server started in the FastAPI lifespan, `ENABLE_GRPC=true`). The separate `veritas-grpc` container is gone. |
| Envoy | `envoy/*.yaml` (generated by `scripts/gen_envoy.py`): HTTP listener → host `:8000`, gRPC listener (HTTP/2 connection manager, **not** tcp_proxy) → host `:50051`, admin + Prometheus metrics `:9901`, JSON access logs on stdout. |
| Test operations | HTTP `GET /api/v1/quizzes/{quiz_id}`; gRPC **`ExamService/GetQuiz`** (new read-only unary RPC, `proto/…/exam.proto`, stubs in `gen/` regenerated). |
| Replica identity | Logs: `replica.id`. Metrics: `replica` label added by Prometheus per scrape target. Responses: `X-Replica-Id` header / `x-replica-id` gRPC metadata (so Envoy logs the selected replica and the client can count shares itself). |
| Trace correlation | Clients send `X-Trace-Id` / `x-trace-id`; Envoy forwards it unchanged and logs it as `trace.id`; replicas log the same id. |
| Shared state | Login rate-limit counters moved from process memory into the shared DB (`DbSlidingWindowLimiter`); see below. |
| Observability | Prometheus scrapes A, B, C and Envoy directly; new dashboard `veritas-a3-load-balancing.json`; Filebeat also keeps Envoy's JSON log (`service.name: veritas-envoy`). |
| Tools | `scripts/load_client.py` (fixed-rate open-loop client), `scenario.py`, `failure_run.py`, `envoy_log_shares.py`, `build_dashboard_a3.py`, `gen_envoy.py`. |
| Housekeeping | Grafana datasource + dashboard-provider files added (`a3-datasource.yml`, `a3-provider.yml`); Dockerfile runs uvicorn with `--proxy-headers` so the login limiter keys on the real client IP behind Envoy. |

## Architecture
```
 HTTP clients ─► Envoy :8000 (http_ingress) ─┐   route "/"                       ┌─► veritas-a  172.28.0.11  HTTP+gRPC  (A)
                                             ├── cluster http_backend ───────────┼─► veritas-b  172.28.0.12  HTTP+gRPC  (B)
 gRPC clients ─► Envoy :50051 (grpc_ingress) ┘   cluster grpc_backend (HTTP/2) ──┴─► veritas-c  172.28.0.13  HTTP+gRPC  (C)
                                                                                         │ all three mount the same volume
                                                                                         ▼
                              /data/veritas.db  (SQLite, WAL)  = users, quizzes, sessions, attempts (idempotency), rate-limit hits
 Prometheus ─scrapes directly─► veritas-a/b/c:8000/metrics , envoy:9901/stats/prometheus      (not via the balanced route)
 Filebeat ─► Elasticsearch ─► Kibana   (replica ECS logs + Envoy JSON access logs)
```
Replicas have fixed IPs so Envoy uses STATIC endpoints: a stopped replica stays a known endpoint and only the **active health checker** removes/restores it (not Docker DNS).

## Shared or per-replica?
| State | Where | Shared? | If it were per-replica |
|---|---|---|---|
| Data (users, quizzes, sessions, attempts) | SQLite file on volume `veritasdata` (WAL, `BEGIN IMMEDIATE` writers) | **shared** | each replica would show different quizzes/history |
| Idempotency records | `attempts` row with `UNIQUE(session_id)` in the same DB, decided inside the write transaction | **shared** | a retry landing on another replica would create a second attempt |
| Rate-limit counters | **were** in-process memory (A2) → now table `rate_limit_hits` in the shared DB | **shared (changed)** | the 5/60 s budget would be per replica (≈15/60 s with 3 replicas), `Retry-After` inconsistent, a restart resets the counter |
| Still per-replica (unchanged, documented) | A2 fault-injection state, the "every 5th submit is slow" counter, `/internal/delay`, Prometheus metrics (each replica counts only its own traffic — that is what the dashboard compares) | per replica | `veritas_active_test_takers` is derived from the DB, so each replica reports the same value (do not `sum()` it) |

## Scenarios (Envoy config = one generated file each)
| Command | Policy | Used in |
|---|---|---|
| `python scripts/scenario.py a-only` | A only (B, C running, not destinations) | Part A/B baseline |
| `python scripts/scenario.py rr` | round robin 1:1:1 | Part C, D (reference) |
| `python scripts/scenario.py weighted` | round robin 2:1:1 | D1 |
| `python scripts/scenario.py least-request` | least request (`choice_count: 3` = compares all 3), 1:1:1 | D2 |
| `python scripts/scenario.py health` | round robin 1:1:1 + active health checks | D3 |

Envoy runs with `--concurrency 1` (one round-robin sequence → repeatable shares; with several worker threads each has its own sequence and shares are only ≈1/3). Circuit breakers are set so high they never trip, and there is no `retry_policy` (no retries); the client has no retries either.
Regenerate after editing `scripts/gen_envoy.py`: `python scripts/gen_envoy.py`. Dashboard: `python scripts/build_dashboard_a3.py`.

## Workload (same for every run)
```bash
python scripts/load_client.py http --rate 100 --duration 120 --label "C rr" --out results/c-rr-http.json
python scripts/load_client.py grpc --rate 100 --duration 120 --label "C rr" --out results/c-rr-grpc.json
```
Open loop: request *i* is sent at *i/rate* s regardless of earlier responses. The JSON has: target/achieved rate, sent, success, failed, error rate, client p50/p95/p99, per-replica counts/shares (from `X-Replica-Id`), and sample trace ids. gRPC uses **one connection**. Run HTTP and gRPC one after the other (report them separately).

## Experiments
Always start from `rr` with no delay; always restore afterwards.
```bash
# Part B   python scripts/scenario.py a-only   -> run both clients  (expect 100/0/0)
# Part C   python scripts/scenario.py rr       -> run both clients  (expect ~33/33/33)
# D1       python scripts/scenario.py weighted -> run both clients  (compare with 50/25/25), then: scenario.py rr
# D2 (same delay and workload twice)
curl -X PUT "http://localhost:8002/internal/delay?delay_ms=200"        # B only (direct port; Envoy answers 404 for /internal)
python scripts/scenario.py rr             && <run both clients>
python scripts/scenario.py least-request  && <run both clients>
curl -X PUT "http://localhost:8002/internal/delay?delay_ms=0"          # restore
# D3 failure and recovery (health checks: interval 2s, timeout 1s, unhealthy 2, healthy 2)
python scripts/scenario.py health
python scripts/failure_run.py http --rate 100 --duration 120 --stop-at 30 --start-at 75 --out results/d3-http.json
python scripts/failure_run.py grpc --rate 100 --duration 120 --stop-at 30 --start-at 75 --out results/d3-grpc.json
```
**Recovery commands** (if a run is interrupted): `docker compose start veritas-b`, `curl -X PUT "http://localhost:8002/internal/delay?delay_ms=0"`, `python scripts/scenario.py rr`.

## Where to read the results
* Grafana → **Veritas A3 Load Balancing**: per replica rate, share %, active requests, p50/p95 (1 m `rate()` window), errors by status — HTTP row and gRPC row; Envoy row (upstream responses by class, healthy members, health-check results).
* Client numbers: the JSON files. Envoy-vs-client cross-check (wait ~10 s after the run so Envoy's log is flushed):
  `docker logs veritas-envoy --since 5m 2>&1 | python scripts/envoy_log_shares.py --path /api/v1/quizzes/` (HTTP) and `--path /veritas.exam` (gRPC).
* Kibana (data view `veritas-logs-*`), one search per interface — take a trace id from `sample_trace_ids` of the matching client JSON:
  `trace.id : "<id>"` → two events: `service.name: veritas-envoy` (fields `interface`, `replica.id`, `upstream.host`, `http.response.status_code`, `grpc.status`, `envoy.duration_ms`) and `service.name: veritas-app` (`replica.id`, `event.action: quiz_served`; gRPC ones have `rpc.system: grpc`). Both carry the same `replica.id`.
* Prometheus (http://localhost:9090) examples: share `100 * sum by (replica)(rate(veritas_http_requests_total{route="/api/v1/quizzes/{quiz_id}"}[1m])) / scalar(sum(rate(veritas_http_requests_total{route="/api/v1/quizzes/{quiz_id}"}[1m])))`; p95 `histogram_quantile(0.95, sum by (le, replica)(rate(veritas_grpc_server_handling_seconds_bucket{grpc_method="GetQuiz"}[1m])))`; healthy hosts `envoy_cluster_membership_healthy`.
* Metric labels are only `replica`, `route` (template), `method`, `status`, `grpc_method`, `grpc_code` — no user/session/trace ids.

## Notes / limits
* One SQLite file shared by three containers is fine for a demo (WAL + busy_timeout); real deployments use Postgres. Writes from 3 replicas serialize on the DB lock — the test traffic is read-only.
* Envoy is a single point of failure (see conclusions in the report). `/internal/*` is blocked at the Envoy HTTP listener.
* Not done (optional in the brief): consistent hashing / 4th replica.
